# 问题记录与迭代清单

> 目的：复盘与迭代。每条记录：现象 → 根因 → 是否真实需求 → 修复建议 → 状态。
> 来源：V3/V4 验证与首轮真实评测（2026-09-17，DVWA，DeepSeek，3 次跑批 1 次完成）。

## P1：重放 diff 因留痕截断产生假阳性

- **现象**：重放结果常显示 `body_changed: true`，但内容差异可能只是 proxy.jsonl 留痕时被截断（`RESP_BODY_LIMIT=64KB`），并非真实变化。
- **根因**：`proxy/audit_proxy.py` 落盘只存前 64KB 响应体；重放拿新响应（最多 64KB 切片）与截断旧响应做全量字符串比较。
- **是否真实需求**：是。回放/diff 是 V3 的核心卖点，假阳性会让用户不信任 diff 结果。
- **修复建议**：比较前把双方都截到同一上限再比（`min(len(a), LIMIT)` vs `min(len(b), LIMIT)` 语义），或 diff 里标注"响应超长已截断，diff 仅基于前 64KB"；长期可将 RESP_BODY_LIMIT 调大。
- **工作量**：小（几行 + 单测）。
- **状态**：✅ 已修（2026-09-17）：diff 前双方截到 RESP_BODY_LIMIT 对齐，超长时返回 `truncated_comparison: true` 并在 UI 标注；单测覆盖。

## P2：证据有效率低（首轮实测 0.4）

- **现象**：完成会话的 6 条 findings 引用 10 个 evidence request_id，仅 4 个有效；如"命令注入 RCE"引用的 #23/#28 都指向 `/vulnerabilities/sqli/` 而非 `/exec/`，"LFI"引用的也是 sqli 的请求。
- **根因**：两层——(a) 模型引用了"同方向里随便一条请求"而非"证明该漏洞的那条请求"；(b) 打分器要求证据 URL 模块 ∈ 发现声称的模块，但像"安全等级 Cookie 降级"这类跨模块发现天然引用别处请求，被记为无效。即：模型引用不精确 + 评分规则对跨模块发现过严，两者叠加。
- **是否真实需求**：是。证据可溯源是项目的核心契约（"每条结论必须引用 request_id"），证据无效 = 结论不可复现，直接伤害产品价值；也是 V4 查准/查全数字可信的前提。
- **修复建议**：
  1. prompt 侧：submit_report schema 增加每条 evidence 一句 `why`（该请求证明了什么），强制模型自查相关性；
  2. 打分侧：把"证据 URL 模块匹配"放宽为"匹配 ∨ 发现的 rationale 中提到了该模块路径"，减少跨模块发现的误判；
  3. 评测侧：把"证据有效性"拆成 `存在性` 与 `指向性` 两个指标分别看，避免一个问题掩盖另一个。
- **工作量**：中（prompt + scoring 各一小块，评测重跑对照）。
- **状态**：✅ 已修（2026-09-17）：evidence schema 升级为 `{request_id, why}`（int 旧格式向后兼容），prompt 强制引用"证明该漏洞的那条请求"；打分器指向性放宽（rationale 命中模块关键词即可）；指标拆分为 `evidence_existence`（存在性）与 `evidence_validity`（指向性）。待下次真实评测验证数字改善。

## P3：长对话间歇性 llm_error（首轮 3 跑 2 挂）

- **现象**：两次会话在 83 条 messages（约 16 万字符，42-47 步）处 `llm_error` 失败，报告为空。事后把失败会话的真实 messages 重放同一轮调用——成功。失败是间歇性的。
- **根因**：`agent/llm.py` 对 60s 超时/5xx 做固定 4 次重试，但两次失败都在对话很长时发生，最可能是 DeepSeek 长上下文请求偶发超时/限流；固定重试间隔（短）在长请求场景下不够。真实需求无争议：完成率 0.33 直接让评测与产品不可用。
- **是否真实需求**：是。完成率是 V4 一切指标的分母。
- **修复建议**：
  1. 失败分类落盘：llm_error 时把 HTTP 状态/异常类型写进 report.notes（现在只有 `llm_error` 一个词，无法区分超时/限流/4xx），评测报告才能归因；
  2. 重试策略随消息长度自适应：长对话加长超时（60s→120s）与重试间隔（指数退避已有，加大系数）；
  3. 兜底：强制收卷轮失败时，截断历史（保留 system + 最近 N 条 + 方向汇总）再试一次，而不是直接放弃整场会话。
- **工作量**：中。
- **状态**：✅ 已修（2026-09-17）：LLMError 带 kind（timeout/transport/http_<code>）落盘到 stopped_reason（`llm_error:timeout` 等）；超时随 payload 自适应（60s 起步、封顶 180s）+ 指数退避；强制收卷轮失败时截断历史（system+首条+最近 12 条）再试一次。

## P4：单方向预算导致查全率低（recall 0.231）

- **现象**：37 步只命中 sqli/exec/fi 三个模块，13 个 GT 模块漏 10 个。
- **根因**：V2 双层循环的方向预算（15 步/方向、总 40 步）天然只够 2-3 个方向；且模型倾向深挖单模块拿"确凿证据"而非广撒网。这是预算机制与策略的取舍，不是 bug。
- **是否真实需求**：部分是。产品定位是"深度验证、证据可溯源"，查全率低本身可接受；但**评测想衡量的是上限**，可以在评测中引入"广度模式"（如 `max_steps_per_direction` 调小、或总步数加大）作为对照实验，不必改默认行为。
- **修复建议**：作为评测参数而非产品改动——`python -m eval --broad` 传入更碎的方向预算，对比 depth/broad 两种策略的 P/R 曲线。
- **工作量**：小（CLI 传参即可，机制已有）。
- **状态**：未修（记录为实验方向）。

## P5：重放不带认证态（已修，V3.1）

- **现象**：重放需要登录的页面得到 302 跳登录，diff 无意义。
- **根因**：proxy 留痕不含请求头，重放无法复现会话。
- **修复**：V3.1 已修——留存认证相关头（cookie/authorization 等 6 个）到 `req_headers`，重放带回。实测带 PHPSESSID 重放 200→200 命中真实页面。
- **状态**：✅ 已修（2026-09-17，commit 6644ec1）。注意：仅对 V3.1 之后的新会话生效。

### 新发现问题

## P2a：指向性差的真正原因——模型用"扫过路径"当证据

- **现象**：第二轮 9 条 evidence 全部存在（存在性 1.0），但只有 3 条指向声称的模块。如"命令注入"引用了 `http://target:8080/`（根路径），"LFI"引用了 `http://web:8080/`；且 URL host 出现 `target`、`web` 等容器内别名（会话目标是 127.0.0.1）。
- **根因**：(a) 模型把"证明漏洞的那条请求"理解为"探测过程中扫过的任意请求"，引用的是 curl 命令序列而非 exploit 命中那条；(b) 沙箱内 `curl` 解析目标 host 走了容器 hosts 别名，留痕 URL 与 meta 目标不一致——这也解释了为什么有些 URL 不含 `/vulnerabilities/`。
- **是否真实需求**：是。指向性是"证据可溯源"的核心；host 别名还影响白名单判断的直观性（当前白名单按三元组匹配别名同样放行，功能没坏但留痕难读）。
- **修复建议**：
  1. proxy 侧：把上游真实 host 规范化（按白名单三元组重写留痕 URL 的 host:port），让留痕 URL 与用户输入一致；
  2. prompt 侧：给出正例——"evidence 必须是**响应里出现漏洞特征的那条**（如含 UNION 回显、/etc/passwd 内容、id 输出的响应）"，并在 schema 的 why 描述里强调"响应内容证明"；
  3. 评测侧：已拆分的两个指标继续分报，跟踪指向性趋势。
- **工作量**：中。
- **状态**：部分已修（2026-09-17）：(1) proxy 留痕 URL 已规范化为白名单登记目标（转发仍用原始 host，请求语义不变），留痕不再出现 target/web 别名；(2) prompt 增加正例（引用含 UNION 回显 / id 输出 / /etc/passwd 内容的那条响应）与反例。指向性数字待下轮评测验证。

### 新发现问题

## P2b：指向性方差大——弱引用惩罚缺失，模型对"引用哪条"无压力

- **现象**：同版本同 prompt，一次指向性 0.833、一次 0.125。差的那次把 `security.php`、`view_source.php` 这类"路过页面"的请求当证据，而真正的 exploit 请求（如 #31 POST /exec/）就在留痕里却没被引用。
- **根因**：evidence 契约只有"非空 + request_id 存在"的硬校验，没有指向质量压力；why 字段模型可以随便写一句话过关。模型对引用选择本质上是随机的，引导词只能影响不能约束。
- **是否真实需求**：是，且是 P2 的最后一公里。查准已满分，指向性成为证据可信度的短板。
- **修复建议**（按性价比排序）：
  1. **评测期自动重引**（推荐，不改产品）：打分时对每个 finding 在 proxy 留痕里自动搜索"更优证据"（URL 模块匹配 + 响应体含漏洞特征的记录），若存在则把该 finding 的指向性按重引结果计——衡量"证据是否可得"而非"模型是否引用对"；同时报告"模型引用 vs 最优可引用"的差距作为 prompt 迭代依据。
  2. 循环内校验强化：submit_report 校验 evidence 的 why 是否非空字符串且 >10 字符，空泛 why 打回重报（已有 report_retried 机制可复用）。
  3. 训练数据路线：messages.jsonl 已在积累，未来可用评测的重引结果做偏好对做微调。
- **工作量**：中（方案 1 最小）。
- **状态**：✅ 方案 1 已实现（2026-09-17）：scoring 新增 `best_available_evidence`（留痕中搜索"模块匹配 + 响应非空"的更优证据），指标新增 `evidence_available_ratio`（可得性）与 `model_cited_well_ratio`（模型引用好）。对第三轮两会话离线重打分：可得性均 1.0，模型引用好仅 0.143 / 0.667——证实证据可得而模型没引用对，后续迭代方向为方案 2（why 非空校验打回）与训练数据微调。
